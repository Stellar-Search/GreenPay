# Runbook: Tracing a Donation by Correlation ID

**Issue:** #374 — Cross-cutting correlation identifier  
**Applies to:** GreenPay backend (all environments)

---

## Overview

Every donation attempt carries a **correlation identifier** (`correlationId`) — a UUID v4 generated by the client (or by the backend if the client does not supply one) and propagated through:

| Boundary | How the id travels |
|---|---|
| Client → HTTP handler | `X-Correlation-ID` request header |
| HTTP handler → Express logs | `AsyncLocalStorage` context, written to every JSON log line |
| HTTP handler → Event store | Stored in `event_stream.payload->>'correlationId'` |
| HTTP handler → pg-boss job | Embedded in the job's `data.correlationId` column |
| Background job → logs | `runWithCorrelationId` re-enters the ALS context at job start |
| Any log line → operator | Every JSON line contains `"correlationId": "..."` |

---

## Step-by-step Retrieval Procedure

### 1. Obtain the correlation ID

**From the donor / client:**  
Ask the donor for the value of the `X-Correlation-ID` header they sent, or the `correlationId` returned in the API response body's error object.

**From the HTTP response (automated clients):**  
```
X-Correlation-ID: <uuid>
```
This header is set on every response by the `correlationIdMiddleware`, even on 4xx/5xx responses.

**From recent logs (if the id is unknown):**  
Search by `transactionHash` instead — see step 2b below.

---

### 2. Query the structured logs

All log lines are newline-delimited JSON. Pipe to `jq` for filtering.

#### 2a. Filter by correlation ID
```bash
# File-based logs (e.g. stdout redirected to a file)
jq -c 'select(.correlationId == "YOUR-CORRELATION-ID")' /var/log/greenpay/app.jsonl

# Docker / Kubernetes (last 1 000 lines)
kubectl logs deployment/greenpay-backend --tail=1000 \
  | jq -c 'select(.correlationId == "YOUR-CORRELATION-ID")'
```

#### 2b. Filter by transaction hash (when correlationId is unknown)
```bash
jq -c 'select(.transactionHash == "YOUR-TX-HASH")' /var/log/greenpay/app.jsonl
```
The first line matching the hash will contain the `correlationId`, which you can then use for the full trace.

#### 2c. Filter by donor address
```bash
jq -c 'select(.donorAddress == "GDONOR...")' /var/log/greenpay/app.jsonl
```

---

### 3. Query the event store (PostgreSQL)

```sql
-- All events for a correlation ID (ordered chronologically)
SELECT
  event_id,
  event_type,
  aggregate_type,
  aggregate_id,
  occurred_at,
  payload->'data'->>'transactionHash' AS tx_hash,
  payload->>'correlationId'           AS correlation_id
FROM event_stream
WHERE payload->>'correlationId' = 'YOUR-CORRELATION-ID'
ORDER BY occurred_at ASC;
```

> **Note:** Events stored before this change (PR #374) will not have a `correlationId` in their payload. Use the `transactionHash` column to find those.

```sql
-- Fallback: find by transaction hash
SELECT *
FROM event_stream
WHERE payload->'data'->>'transactionHash' = 'YOUR-TX-HASH';
```

---

### 4. Query the job queue (pg-boss)

```sql
-- Active, completed or failed jobs for this correlation ID
SELECT
  id       AS job_id,
  name     AS queue,
  data->>'projectId'      AS project_id,
  data->>'correlationId'  AS correlation_id,
  state,
  createdon,
  startedon,
  completedon,
  output
FROM pgboss.job
WHERE data->>'correlationId' = 'YOUR-CORRELATION-ID'
ORDER BY createdon ASC;

-- Dead-letter queue (permanently failed jobs)
SELECT *
FROM pgboss.job
WHERE name = 'ai-summary-dlq'
  AND data->>'correlationId' = 'YOUR-CORRELATION-ID';
```

---

### 5. Correlate with Horizon

The `transactionHash` found in step 3 can be looked up on Stellar's network explorer:

- **Testnet:** `https://stellar.expert/explorer/testnet/tx/<TRANSACTION-HASH>`
- **Mainnet:** `https://stellar.expert/explorer/public/tx/<TRANSACTION-HASH>`

Or via the Horizon API directly:
```bash
curl "https://horizon-testnet.stellar.org/transactions/YOUR-TX-HASH"
```

## Complete Timeline Example

Given `correlationId = "c1a2b3d4-..."`:

```
[log]   "donation attempt"     correlationId=c1a2b3d4 donorAddress=G... transactionHash=abc...
[log]   "donation recorded"    correlationId=c1a2b3d4 donationId=<eventId> amountXlm=50
[event_stream]  DonationRecorded  occurred_at=T+0ms  payload.correlationId=c1a2b3d4
[log]   "AI summary job enqueued"  correlationId=c1a2b3d4 projectId=... jobId=<pgboss-id>
--- async boundary: job runs in a later session ---
[log]   "summary job started"  correlationId=c1a2b3d4 projectId=... jobId=<pgboss-id>
[log]   "summary job completed" correlationId=c1a2b3d4 model=summary-model-v1
```

## Security Notes

- **No log line will ever contain a Stellar private key** or a full signed transaction envelope — these are redacted to `[REDACTED]` by `src/utils/logger.js` before the line is written. This is asserted by an automated test (`logger.test.js` guard tests).
- The `correlationId` itself is a UUID and contains no personally identifiable information.
- Wallet addresses (`donorAddress`, `donorPublicKey`) are public keys and safe to log.
